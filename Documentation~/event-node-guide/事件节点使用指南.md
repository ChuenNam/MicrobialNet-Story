# 事件节点使用指南

> 本文档面向**第一次接触事件节点**的使用者。只讲"怎么用"，不解释底层原理。
> 看完照着做，就能让剧情在指定位置"暂停等一件事做完，再继续"。

---

## 事件节点是干什么的 {.overview}

事件节点 = 剧情里的一扇 **具名闸门**（对使用者来说，体验上就是一个**暂停点**）。

剧情走到这个节点会**停下来**，等游戏程序完成某件事——比如弹出一个界面、播放一段动画、打一场战斗——**做完之后剧情才继续往下走**。

一个事件节点只有两个可以填的东西：

| 字段 | 作用 | 必填 |
|---|---|---|
| **事件名** | 这扇闸门的名字，例如 `confirm:battle_start` | 必填 |
| **参数 (JSON)** | 业务自管的数据袋（逃生口，极少用，见第四章） | 可选 |

> **边界（一句话版）**：事件节点只负责「在这里停下来、喊一个名字、等回应」。喊完之后发生什么、怎么做，全部归游戏程序；剧情图里只放**叙事决策**（变量、分支），**不放业务数据**。
> 想传信息给事件时，请先看第四章的「三条通道」再决定要不要碰参数框。

## 要传信息给事件？先选「走哪条通道」

> 事件节点是闸门，不是数据袋。它向游戏程序声明一个**时刻**（在此暂停/在此通知）；信息按**语义**分流到三条通道之一。**业务数据不进图**——这是本工具的功能边界（设计依据见《技术架构文档》§3 D4 的「具名闸门」边界宣言）。

| 你的信息是…… | 走哪条通道 | 怎么做 |
|---|---|---|
| **叙事内容**：谁是敌人、第几周目、好感度 | ① **变量**（前置节点） | 事件节点**前**用「赋值」/「条件」节点把值写进剧情变量；程序侧读变量；业务做完还能**写回**变量供后续分支消费 |
| **引用凭证**：播哪段 CG、开哪场战斗、哪个关卡 | ② **事件名**本身 | 名字直接带后缀：`cutscene:cs_012`、`battle:elite_03`（参照既有约定 `voice:{key}`）。下拉与运行时注册同源，选不错 |
| **业务自管杂项**：前两条都装不下 | ③ **参数 (JSON)**（逃生口） | 极少用。工具不理解其内容，只兜底校验 JSON 语法（写错红条 + 拦打包） |
| **平衡数值/业务配置**（等级、伤害、掉率……） | ❌ **三条通道都不走** | 数据的家在程序自己的配置里（Excel/SO）。放进图 = 同一份数据两个源头，两边各改各的迟早打架 |

### 推荐用法示范：一场战斗闸门（参数框全程留空）

「打一场由**剧情决定**敌人的战斗，打赢/打输走不同分支」：

1. **闸门前**（叙事决策进图）：用「赋值」节点把本次敌人写进变量 `battle_enemy`——值可以来自更早的玩家选择分支，这样「打谁」是剧情说了算。
2. **闸门**：事件节点填 `confirm:battle_start`，参数(JSON) **留空**。
3. **程序侧**（业务读变量、写回结果）：注册的事件从变量读 `battle_enemy` 开打；打完把 `battle_won` 写回变量，调 `onComplete()`（代码见第五章「闸门闭环」）。
4. **闸门后**（叙事消费结果）：接「条件」节点判断 `battle_won` → 走胜利/失败两条分支。

这个形态的收益：敌人选择是**剧情决策**（可校验、可存档、试跑可回放）；战斗结果是**剧情可消费的变量**（后续任何节点可引用）；没有任何数据在图里和程序配置里各存一份。

### 什么时候才真的需要③参数(JSON)

- 一次性、业务自己消化的琐碎信息（如某埋点的扩展字段）；
- ①②都不适合的引用集合。

即使这时也记住：参数是**给程序的数据袋，不是策划的编辑对象**——工具不为它提供字段校验与表单（这是设计边界，不是待办功能）。语法写错有红条兜底；**字段名写错工具帮不了你**，要靠程序侧约定。

```json
{ "enemy": "slime", "level": 3 }
```

> 上面这段恰恰是**反面示范**：敌人是叙事内容（该走①变量），等级是平衡数值（该住程序配置）——两条都塞进数据袋，工具对其中任何一条都无法把关。
> 参数语法校验仍然生效：非法 JSON 会显示红色错误条（`事件参数(JSON)语法非法`）并拦截打包。

## 如何自定义事件

> ⚠️ **重要**：如果只定义了事件，**没有在游戏程序里注册对应的事件**，剧情会**直接跳过**这个节点。

要让事件节点起作用，需要程序在游戏启动时，把"事件名"和"要做的事"关联起来。下面给两种最常用、最简单的写法。

### 方式 A：最简单（几行代码）

```csharp
var bus = new StoryEventBus();
bus.Register("confirm:battle_start", (payloadJson, onComplete) =>
{
    // 在这里做你的事：弹界面 / 播动画 / 开始战斗……
    Debug.Log("战斗开始了！");

    // 事情做完后，调用 onComplete()，剧情才会继续往下走：
    onComplete();
});
storyFlow.Configure(new StoryFlowConfig { Events = bus });
```

**记住一句话：一定要调用 `onComplete()`，否则剧情会永远停在这个节点。**

### 方式 B：更规整（类 + 特性，推荐）

```csharp
[StoryEvent("confirm:battle_start")]   // 名字要和节点里填的完全一致
public class BattleStartEvent : IStoryEvent
{
    public string EventName => "confirm:battle_start";   // 名字同上——运行时按它注册，编辑器下拉也按它收集

    public void Execute(string payloadJson, Action onComplete)
    {
        // 在这里做你的事：弹界面 / 播动画 / 开始战斗……
        Debug.Log("战斗开始了！");

        onComplete();   // 做完后调用，剧情继续
    }
}
```

> 两处名字**必须一致**：运行时按 `EventName` 注册，编辑器下拉也取 `EventName`（`[StoryEvent]` 特性只负责让类被发现）。
> 写得不一致时，校验面板会出现黄色警告（`特性名与 EventName 不一致`）提醒你修正——别忽略它，否则会出现「下拉里选得到、游戏里却没反应」的问题。

然后在游戏启动时注册它：

```csharp
var bus = new StoryEventBus();
bus.Register(new BattleStartEvent());
storyFlow.Configure(new StoryFlowConfig { Events = bus });
```

> 用方式 B 注册后，编辑器的事件名下拉里会**自动出现** `confirm:battle_start`，策划直接选就行，不用手打，也不容易写错。

### 闸门闭环：程序侧怎么读写剧情变量

第四章示范的「变量进、变量出」依赖一个关键事实：**变量提供者由宿主自己创建并注入**——注入给剧情系统的同时自己留着引用，业务侧就能随时读写剧情变量。

```csharp
// ① 宿主自建变量黑板（局部变量定义可从图资产取，全局变量另配）
var variables = new InMemoryVariableProvider(localVariableDefs, globalVariableDefs);

var bus = new StoryEventBus();
bus.Register("confirm:battle_start", (payloadJson, onComplete) =>
{
    // ② 读：剧情侧用「赋值」节点写好的叙事决策（谁是敌人由剧情说了算）
    variables.TryGetValue("battle_enemy", out var enemy);

    // ……开打。打完：
    // ③ 写回：让闸门后的「条件」节点能按结果分支
    variables.SetValue("battle_won", true);

    onComplete();   // 闸门关闭，剧情续走
});

// ④ 注入剧情系统（同一份 variables——这就是闭环）
storyFlow.Configure(new StoryFlowConfig { Events = bus, Variables = variables });
```

> 读用 `TryGetValue(变量id, out 值)`，写用 `SetValue(变量id, 值)`——与「赋值/条件」节点操作的是**同一块黑板**，所以图里的后续节点立刻能看到业务写回的结果。

# 其他

## 常见问题

| 现象 | 原因 | 解决办法 |
|---|---|---|
| 事件节点一闪而过，没有暂停 | 事件名没在程序里注册，或没注入 Events | 检查第五章，确认 `bus.Register(...)` 和 `storyFlow.Configure(...)` 已执行，且注册的名字和节点里填的**完全一致** |
| 剧情卡在事件节点不动了 | 程序里漏了 `onComplete()` 调用 | 在事件逻辑结尾补上 `onComplete();` |
| 下拉里没有我要的事件名 | 程序没用方式 B 注册 `[StoryEvent]` | 让程序用方式 B 注册，或用手填方式 A 时相同的名字 |
| 参数读不到内容 | JSON 格式写错 | 检查引号、逗号，确保是合法 JSON |
| 业务写回的变量，闸门后的条件节点读不到 | 事件里操作的变量提供者与剧情系统用的**不是同一份** | 按第五章「闸门闭环」：宿主**自建** provider 注入 `StoryFlowConfig.Variables` 并自留引用，别在事件里另外 new 一块黑板 |
| 想把等级/伤害等平衡数值塞进参数框 | —— | 别塞（见第四章❌行）：数据住程序配置；图里只放叙事决策（变量）与引用凭证（事件名） |
